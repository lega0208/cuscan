# CubeCL engineering findings for fast-umap

## Scope and evidence

This is a source-based review of the entire CubeCL book navigation in [`references/cubecl-book/SUMMARY.md`](cubecl-book/SUMMARY.md), with the relevant current implementation checked in [`Cargo.toml`](../Cargo.toml), [`src/backend.rs`](../src/backend.rs), [`src/cuda_backend.rs`](../src/cuda_backend.rs), and standard-UMAP kernels ([`ann.rs`](../src/kernels/standard_umap/ann.rs), [`graph.rs`](../src/kernels/standard_umap/graph.rs), [`layout.rs`](../src/kernels/standard_umap/layout.rs), [`query.rs`](../src/kernels/standard_umap/query.rs)). Paths and API spellings below refer to the checked-in book/repository sources, not an independently verified current CubeCL release.

The book's tested tutorials target CubeCL 0.11.0. This repository is Rust edition 2024; `Cargo.toml` uses stable semver requirements `cubecl = "0.11.0"` and `burn`/`burn-cubecl = "0.22.0"` (the direct CubeCL dependencies are optional), not exact-version constraints. The checked-in `Cargo.lock` currently resolves these packages to CubeCL 0.11.0 and Burn/burn-cubecl 0.22.0. The book and current lock therefore align at these crate versions, but future resolution under the manifest requirements may select compatible releases, and actual APIs are routed through Burn's Cube backend. The book is not a guarantee that every statement or backend matrix reflects every runtime/compiler combination; check the lockfile, compiled API, and backend support before adopting examples.

**Evidence labels:** “Book guidance” means directly described by the linked book sections. “Repository observation” means directly visible in the current source. “Hypothesis / experiment” is a proposed optimization opportunity, not an identified defect or measured result. No performance measurements were made for this document.

## Prioritized actions

### P0 — Preserve indexing, bounds, ownership, and race invariants

1. **Make index spaces and launch geometry explicit at every kernel boundary.** The CubeCL topology distinguishes workgroup/cube IDs (`CUBE_POS_*`), local lane coordinates (`UNIT_POS_*`), workgroup dimensions (`CUBE_DIM_*`), total workgroup counts (`CUBE_COUNT_*`), and absolute/global positions. Use a global/absolute position when each lane owns a globally unique output item; use cube and unit coordinates deliberately for tiled or cooperative work. Derive bounds from the actual logical extent and guard padded invocations before any tensor access. A legal per-workgroup dimension does not guarantee a legal total launch, and exceeding a backend limit can produce deferred launch errors (the 3D tutorial demonstrates this). [Parallel Reduction — “CubeCL Constants” and “Parallel Reduction Example”](cubecl-book/getting-started/parallel_reduction.md#cubecl-constants), [Parallel Reduction 3D — “A first try” / “A better approach”](cubecl-book/getting-started/parallel_reduction_3d.md#a-first-try)

   **Repository observation:** Standard kernels have fixed launch dimensions (`ANN_CUBE_DIM=32`, `GRAPH_CUBE_DIM=32`, `LAYOUT_CUBE_DIM=64`, `QUERY_CUBE_DIM=1`) and use absolute X positions with explicit shape guards in several stages. Query uses one lane per query row while walking a graph/search procedure serially within the lane; graph's prefix stage deliberately uses one lane to scan counts. These are meaningful algorithm/parallelism choices, not evidence of incorrectness. [ann.rs](../src/kernels/standard_umap/ann.rs), [graph.rs](../src/kernels/standard_umap/graph.rs), [layout.rs](../src/kernels/standard_umap/layout.rs), [query.rs](../src/kernels/standard_umap/query.rs)

   **Hypothesis / experiment:** For ANN and query, profile separate stages and vary lane-to-row mapping or cooperative feature-distance work only where occupancy and data shape justify it. Keep a scalar reference and compare exact neighbor/quality invariants, race safety, and small/boundary sizes. Query's `CubeDim(1)` could leave GPU parallel capacity unused for many independent queries, but the kernel has per-query scratch and serial search work; a larger launch mapping is not automatically faster or safe.

2. **Treat output ownership as a correctness proof, especially for atomics and scatter.** Establish which invocation owns each output element; if ownership is shared, use the required atomic operation or a staged reduction/scatter. Separate launches on the same ordered stream can establish stage ordering, but a barrier among arbitrary cubes cannot be assumed. The reduction chapter explicitly warns that each invocation must write a distinct output; graph construction demonstrates atomic counting/cursors followed by scatter and sorting as separate stages. [Parallel Reduction — “Parallel Reduction Example”](cubecl-book/getting-started/parallel_reduction.md#parallel-reduction-example), [Configuration — “Streaming”](cubecl-book/advanced-usage/config.md#streaming)

   **Repository observation:** `fuzzy_graph_count_kernel` atomically counts, prefix runs in one lane, and scatter claims cursor ranges using atomic increments; sort makes per-head order deterministic after atomic scatter. Layout's shared embedding path atomically reads and updates coordinates; its source documents the CUDA-specific reason for the atomic add-zero read. Do not replace these with ordinary reads/writes based only on presumed graph structure. [graph.rs](../src/kernels/standard_umap/graph.rs), [layout.rs](../src/kernels/standard_umap/layout.rs)

3. **Keep buffer aliasing and mutation rules explicit.** The book's examples use an immutable input and a distinct mutable output; use that as the safe default when a kernel reads values while producing updated values. In-place updates are valid only if each write cannot affect another lane's still-needed read, or synchronization/atomic semantics make the algorithm correct. Prefer explicit ping-pong buffers for iterative algorithms when they define epoch semantics; account for their copy and allocation costs rather than silently aliasing. [Simple Reduction — “A first example of a GPU reduction with CubeCL”](cubecl-book/getting-started/simple_reduction.md#a-first-example-of-a-gpu-reduction-with-cubecl), [Parallel Reduction — “Parallel Reduction Example”](cubecl-book/getting-started/parallel_reduction.md#parallel-reduction-example)

   **Repository observation:** Layout explicitly copies the old head embedding to a fresh `next` buffer before atomic epoch updates; fit and transform have different shared/fixed-tail contracts, documented in the file header. Preserve and test the `shared_embeddings` distinction and returned-buffer semantics. [layout.rs](../src/kernels/standard_umap/layout.rs)

### P1 — Optimize memory movement, launch costs, and arithmetic with evidence

4. **Investigate contiguous/coalesced access and vectorization only when the layout supports it.** For adjacent lanes reading adjacent scalar addresses, memory transactions are more likely to be efficient; keep the fastest-changing dimension aligned with the lane mapping when algorithmically possible. CubeCL vectorization is a launch-time factor that changes the logical element type/lane behavior; shape and offsets must be interpreted consistently. The vectorized reduction example explicitly divides row length and row offset by the vector width and assumes divisibility, and its displayed speedup is tutorial-hardware evidence only, not a forecast for this project. For tails, non-contiguous tensors, odd dimensions, or unsupported vector widths, provide correct handling rather than assuming divisible shapes. [Vectorization](cubecl-book/core-features/vectorization.md), [Vectorized Reduction — “Application to the reduction problem”](cubecl-book/getting-started/vectorized_reduction.md#application-to-the-reduction-problem)

   **Repository observation:** Current selected kernels operate on flattened row-major-style addresses such as `row * features + feature`, `row * width + slot`, and `row * dimensions + coordinate`. They use Burn `Tensor` indexing rather than explicit `Vector<T,N>` arguments. The host wrappers frequently call `into_contiguous` (see implementations in the cited files), so any vectorization experiment must preserve contiguity and validate tail/alignment behavior at the launch boundary.

   **Hypothesis / experiment:** ANN distance calculation has sequential feature loops per row; benchmark vectorized feature loads or a lane-per-feature reduction on representative feature counts. Measure the complete stage and include conversion/contiguity-copy costs. Test odd/non-multiple feature counts, k/width edge cases, and all enabled backends; do not infer a speedup from the tutorial's ~3× result.

5. **Reduce launches and intermediate traffic only when dependencies permit fusion.** A multi-stage algorithm may need separate ordered kernels for global dependencies; fusion can reduce launch and memory overhead, but can increase register pressure, duplicate work, or inhibit parallelism. The book demonstrates comptime-selected implementations and points to examples of fusion, not a universal rule that fewer kernels win. [Comptime — “Feature Specialization”](cubecl-book/core-features/comptime.md#feature-specialization), [Examples](cubecl-book/getting-started/examples.md)

   **Repository observation:** Fuzzy graph construction uses multiple zero/row/count/prefix/scatter/sort stages, while layout uses clock/copy/update stages. Their intermediate arrays and stream ordering appear semantically intentional. **Hypothesis / experiment:** Use profiling to determine whether launch overhead, memory traffic, atomics, or per-lane loops dominate before considering fusion; any fused variant must retain global ordering, deterministic sort behavior, output validation, and error signaling.

6. **Profile integer division/modulo and expensive scalar math before changing formulas.** The book identifies uniform-but-not-constant division/modulo as a possible cost and describes `FastDivmod` as a backend-dependent optimization; verify the exact type/API and generated backend implementation for this pinned stack. [Math Optimizations — “FastDivmod” and “Backend Support”](cubecl-book/advanced-usage/math_optimizations.md#fastdivmod)

   **Repository observation:** ANN initialization and query use Park–Miller integer division/modulo; query uses `%` for seed/indexing, and layout uses modulo for random sample selection. `smooth_row` contains nested loops over rows/slots and up to 64 binary-search iterations; its work appears potentially substantial, but that algorithm may be required by the desired numerical contract. **Hypothesis / experiment:** Profile these operations separately. Consider precomputed div/mod factors only for repeated divisors supported by a verified API; compare outputs and do not replace arithmetic with approximate shortcuts without quality validation. [ann.rs](../src/kernels/standard_umap/ann.rs), [query.rs](../src/kernels/standard_umap/query.rs), [layout.rs](../src/kernels/standard_umap/layout.rs), [graph.rs](../src/kernels/standard_umap/graph.rs)

7. **Use fast math only behind a demonstrated numerical contract.** CubeCL fast-math flags relax behavior around precision and exceptional values; their effect differs by backend. The book says CUDA/HIP intrinsics described there apply only to `f32`, while other backends currently support none of the listed optimizations; it also flags uncertain CUDA special-value documentation. Scope flags to the narrowest critical function and test NaN/Inf, signed zero, near-zero distances, convergence, and output quality. [Math Optimizations — “Fast Math Options”, “Backend Implementation”](cubecl-book/advanced-usage/math_optimizations.md#fast-math-options)

   **Repository observation:** The graph and layout kernels use `Float` arithmetic, powers/exponentials, clamps, thresholds, and iterative updates. These are numerically sensitive paths; no evidence here establishes a safe tolerance for changing precision. The book's backend matrix is for its documented backends, not proof that every Burn runtime selected in this project maps identically.

### P1 — Specialize portably and benchmark the work users pay for

8. **Use comptime specialization for genuinely static structure, and bound variant growth.** `#[comptime]` may eliminate runtime branches by generating variants; values that are not compile-time known cannot be used in compile-time-only operations (the loop-unrolling example warns that an unknown bound can panic). Feature specialization can select a plane implementation with a fallback and emit separate variants. Avoid unrolling large or data-dependent loops by default: more code/variants can raise compile time and code size. [Comptime — “Loop Unrolling” / “Feature Specialization”](cubecl-book/core-features/comptime.md#loop-unrolling), [Constants — “Plane”](cubecl-book/core-features/constants.md#plane)

   **Repository observation:** Kernel entry points use `#[define(...)]` for element-type specialization, while several algorithm settings arrive as runtime scalar arguments. A candidate optimization is making a small, stable set of parameters comptime only if it measurably removes costly branches/loops without multiplying compile/cache variants. This is a hypothesis; no recommendation to convert existing arguments follows without a profile.

9. **Do not assume a plane size or optional hardware feature.** Plane size is runtime/hardware-dependent according to the book; query the actual feature/property support before using plane operations or specialized data types. Feature specialization should retain a correct portable fallback. CubeCL's book feature table lists backend/compiler-dependent support (e.g. CMMA, f16, f64) and warns that the matrix is specific to listed backends. [Constants — “Plane”](cubecl-book/core-features/constants.md#plane), [Hardware Features — “Querying hardware features” / “Overview”](cubecl-book/core-features/features.md#querying-hardware-features), [Comptime — “Feature Specialization”](cubecl-book/core-features/comptime.md#feature-specialization)

   **Repository observation:** Cargo enables Flex as a CPU backend; CUDA is feature-gated and included in the manifest's default feature list, while `gpu` is a separate feature including WGPU. `StandardUmapOps` is declared for Flex and conditionally Cube/Fusion under `cuda`; the source documents dynamic Burn backend dispatch. CUDA device discovery returns zero/none if unavailable. Thus do not describe WGPU as an enabled default or claim every kernel path is portable across all runtimes: establish the actual Cargo feature set, backend extension registration, supported operations, and fallback behavior for the operation under review. [Cargo.toml](../Cargo.toml), [backend.rs](../src/backend.rs), [cuda_backend.rs](../src/cuda_backend.rs)

10. **Benchmark asynchronous device work with synchronization and separate cold/warm costs.** GPU launches are asynchronous; a host timer around enqueueing is not kernel duration. Synchronize at the measured boundary, return/consume output so work is observable, warm up separately, and report samples/variance, device, backend/compiler, shapes, dtype, and configuration. Separate compilation/autotune/cold-start from steady-state throughput. Tutorial timings are historical examples explicitly device-dependent. [Benchmark — “Implementing the benchmark trait” / “Running the benchmark”](cubecl-book/getting-started/benchmark.md#implementing-the-benchmark-trait), [Autotune](cubecl-book/core-features/autotune.md)

   **Repository observation:** Existing project benches and scripts are present, but this review did not inspect or run them; no current fast-umap performance baseline is asserted. For new CubeCL comparisons use identical input/seed/backend and verify outputs outside the timed loop. Include the full API path where host copies, contiguity conversion, allocation, or multiple kernels are part of normal execution; report kernel-only numbers separately if useful.

11. **Use autotuning as a measured selection mechanism, not a substitute for correct candidates.** CubeCL describes runtime benchmarking of candidate kernels/configurations, cache reuse, and a first-run cost. It may be useful for stable workload regimes and multiple devices, but cache behavior, coverage through Burn's wrappers, and cold-start budget must be verified in this project. Avoid exposing an unbounded configuration search or tuning on correctness-invalid variants. [Autotune](cubecl-book/core-features/autotune.md), [Configuration — “Autotune” and “Cache Location”](cubecl-book/advanced-usage/config.md#autotune)

12. **Use CubeCL logs/configuration to diagnose compilation, profiling, memory, and streaming behavior.** The book documents TOML/environment configuration for profiling, autotune, compilation, memory, and streaming, including CUDA allocator choices and persistent-memory policies. Logging/profiling settings can affect observed behavior; record them and leave production defaults deliberate. Confirm the exact current configuration keys against CubeCL 0.11.0 rather than copying the book's examples blindly. [Configuration — “Overview”, “Profiling”, “Compilation”, “Streaming”, “Memory”](cubecl-book/advanced-usage/config.md#overview)

## Additional maintainability guidance

- **Keep abstractions within CubeCL's supported language subset.** The book documents traits and generated `Expand` traits, including import/supertrait details; structs/enums have derivation and runtime-variant restrictions. Prefer the simplest kernel helpers that compile under the actual proc-macro version; use these features to remove meaningful duplication, not to hide launch behavior. [Trait Support — “Expansion and the expand trait”](cubecl-book/language-support/trait.md#expansion-and-the-expand-trait), [Struct Support — “Defining structs”](cubecl-book/language-support/struct.md#defining-structs), [Enum Support — “Runtime variant restrictions”](cubecl-book/language-support/enum.md#runtime-variant-restrictions)
- **Keep host dispatch concerns separate from device algorithms.** Installation guidance distinguishes runtime features linked by an application from a kernel library's runtime-independent code. In this repository, optional CubeCL dependencies and Burn extension traits are the relevant integration seam; a kernel change should preserve backend availability/feature gating rather than introducing an unconditional runtime dependency. [Installation](cubecl-book/getting-started/installation.md), [backend.rs](../src/backend.rs), [Cargo.toml](../Cargo.toml)
- **Test correctness at shape and concurrency boundaries before performance comparisons.** At minimum include zero/small inputs where allowed, non-divisible tails, invalid indices, duplicate edges, self-edges, empty rows, and deterministic/tie cases relevant to the kernel. This is a repository-specific validation recommendation derived from observed guards, sentinels, duplicate handling and atomic stages, not a list prescribed by the book. Ensure each backend's generated code is exercised; success on Flex alone does not establish GPU race/launch correctness.

## Review refinements: first experiments and acceptance criteria

- **First measure the current layout orchestration, not an idealized single launch.** Shared fit currently splits heads into sixteen ordered batches, following clock preparation and a fresh-buffer copy; transform uses a different launch contract. Attribute time to copy, clocks, batches, and readback separately, then also measure the synchronized complete epoch. Changing batching changes update order and can change embedding quality, even when all accesses remain atomic. Keep fit and transform evaluations separate. [layout.rs](../src/kernels/standard_umap/layout.rs), [Benchmark](cubecl-book/getting-started/benchmark.md)
- **Prioritize bounded candidates.** After attribution, compare a small set of launch geometries for the identified hot stage; then evaluate cooperative/vectorized distance work if feature-loop cost dominates. Test tail shapes and scratch ownership before timing. Consider FastDivmod only for a demonstrably hot repeated divisor, and fast math last because it changes numerical assumptions. These are review priorities, not book-promised speedups. [Parallel Reduction](cubecl-book/getting-started/parallel_reduction.md), [Vectorized Reduction](cubecl-book/getting-started/vectorized_reduction.md), [Math Optimizations](cubecl-book/advanced-usage/math_optimizations.md)
- **Use an explicit acceptance record.** Capture lockfile/features, GPU/runtime/compiler, shapes, seeds, precision, launch geometry, profiling configuration, warm/cold timing distributions and memory cost. Require shape/index/error tests and algorithm-specific quality/determinism checks appropriate to the existing contract, rather than imposing exact coordinate equality on concurrent layout. Keep profiler-enabled and uninstrumented timings separate. [Configuration](cubecl-book/advanced-usage/config.md), [Benchmark](cubecl-book/getting-started/benchmark.md)

## Important uncertainties and source gaps

- The manifest specifies stable semver requirements rather than exact pins. `Cargo.lock` currently resolves `burn` and `burn-cubecl` to 0.22.0 and CubeCL to 0.11.0; re-check the lockfile after dependency updates. Backend compiler versions, generated-code lowering, and Burn's integration behavior still depend on the selected features/runtime and must be checked before adopting low-level examples.
- No CubeCL-specific synchronization/barrier chapter is present in this book TOC. The advice above is limited to ownership, atomics visible in current code, and staged kernels; it does not prescribe a particular barrier primitive or memory-ordering contract.
- The book discusses vectorization and planes conceptually but does not provide a comprehensive memory-coalescing/layout guide. Coalescing suggestions above are conventional performance hypotheses to validate with backend profiling, not claims attributed to a direct book rule.
- The book's hardware feature tables and fast-math backend notes may be incomplete or stale for particular driver/compiler/runtime combinations. Query runtime properties and test each supported feature configuration.
- Current product-code inspection was intentionally limited to the manifest, backend traits/device helpers, and four standard-UMAP kernel files. Other kernels, wrappers, synchronization/streaming setup, benchmark implementations, tests, and locked dependency resolutions were not assessed. There are no measured improvements or identified proven performance regressions in this report.
